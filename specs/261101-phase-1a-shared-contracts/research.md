## Research questions

1. **Badge and "Decide now" (RESOLVED 2026-11-01: match the web app).** The server returns `deskBadgeCount` (new today or overdue) and no `decideNowCount`. Should the app (a) show the server's `deskBadgeCount`, (b) compute "Decide now" client-side as `decideBy` today or `severity = critical` per FR-030 and badge on that, or (c) both? What does the web app show? **Answer:** the web app shows the server's `deskBadgeCount` (`ui/src/lib/attention.ts`, `attentionBadgeCount`) and its "Decide now" shelf is `decideBy` due today or past only, with no severity rule. Decision (owner): match the web app. The app shows `deskBadgeCount` and mirrors the server's `isDecideNow` and `isNewToday` (UTC day boundaries) in domain code so its groups agree with the number. `decideBy` values: `today`, `this_week`, `whenever`, a `YYYY-MM-DD` date, or null.
2. **(ANSWERED in slice 1a-2) Unknown attention kinds.** Eleven source kinds exist. Which ones carry `inlineResolvable` in practice, and what does the minimum viable "Open in web app" fallback need (`subject.href`)?
3. **(ANSWERED in slice 1a-2) Resolver audience.** How should `resolverAudience` (effective resolver policy, addressee) change what the app lets a board user do on an `issue_thread_interaction`? Is a viewer or a non-addressee ever allowed to respond?
4. **(ANSWERED in slice 1a-2) Decision execution.** After `POST /decisions/{id}/decide`, what is the shape of `executionStatus` and the per-effect results, and how long until a terminal state? Needed for the polling use case (FR-043).
5. **(ANSWERED in slice 1a-2) Budget incident resolution.** What does the 422 body look like (unaccounted runs, unpriced usage)? Which fields give the observed spend that the raise amount must exceed (FR-052)?
6. **Role discovery.** `GET /api/cli-auth/me` returns companies and an instance-admin flag; where does the per-company role (owner, operator, viewer) come from, and is `viewer` real at this server version?
7. **(ANSWERED in slice 1a-2) Cache keys.** Which identifiers are stable across factories (company id, item `dismissalKey`, `dedupKey`) for the cache and for undoing a dismissal?

8. **(ANSWERED in slice 1a-2) Where do decision inputs attach?** `DecisionInput` exists in the shared types but `DecisionOption` has no `inputs` field. Check the `GET /api/decisions/{id}` response and the decide request body (`server/src/routes/decisions.ts`). Owner: whoever starts slice 1a-2, before modelling `Decision`.
9. **Role source.** Same as Q6; the answer fixes the `Role` mapping and the permissions table (acceptance criterion 8).

Resolution path for all open questions: answer from the server source or a live authenticated instance (`./scripts/paperclip-test-server.sh up`), record the answer here with the file or response that proves it, then update the data dictionary. Questions 3 to 9 are due before the slice that needs them starts (2 to 5 before 1a-2; 6 and 9 before 1a-1; 7 before 1a-3).

## Answers recorded in slice 1a-1 (server source, Paperclip checkout at `~/Code/Test/paperclip`)

Paths below are relative to that checkout.

**Q6 / Q9 Role source (ANSWERED).** `GET /api/cli-auth/me` (`server/src/routes/access.ts:2885-2898`) returns `{user, userId, isInstanceAdmin, companyIds, memberships, source, keyId}`. `memberships` is a list of `{companyId, membershipRole, status}` built by `resolveBoardAccess` (`server/src/services/board-auth.ts:72-110`), active rows only (`board-auth.ts:93-99`). It carries no company names: names come from `GET /api/companies?scope=accessible` (`server/src/routes/companies.ts:380-400`).
- Server membership roles are `owner`, `admin`, `operator`, `viewer`, `member` (`packages/shared/src/constants.ts:965-979`). `viewer` is real and enforced: a non-safe method by a non-instance-admin viewer fails with `403 "Viewer access is read-only"` (`server/src/routes/authz.ts:111-118`); instance admins skip the check (`authz.ts:111`).
- The server does not distinguish owner from operator on budget routes (`server/src/routes/costs.ts:352-377` only calls `assertBoard` and `assertCompanyAccess`). "Owner only" for budget raise is therefore an app policy from the PRD, not a server rule; the server stays the authority (a 403 is shown).
- Mapping (ADR-011): instance admin, `owner`, `admin` -> Owner; `operator` -> Operator; `viewer`, `member`, anything unknown -> Viewer (fail closed). Per-company role: `isInstanceAdmin` wins over the membership row.

**Challenge create** (`access.ts:2786-2808`, request schema `packages/shared/src/validators/access.ts:73-78`): `POST /api/cli-auth/challenges` body `{command (1-240), clientName?, requestedAccess (default board), requestedCompanyId?}` returns 201 `{id, token, boardApiToken, approvalPath, approvalUrl (nullable), pollPath, expiresAt, suggestedPollIntervalMs: 1000}`. The board API token (`boardApiToken`) is returned at CREATE, not on approval; the challenge `token` and `approvalPath/approvalUrl` embed a secret. Challenge TTL is 10 minutes, board key TTL 30 days (`board-auth.ts:17-18`).
**Poll** (`access.ts:2810-2838`): `GET /api/cli-auth/challenges/{id}?token=<challenge token>` returns the challenge (`id, status, command, clientName, requestedAccess, requestedCompanyId, requestedCompanyName, approvedAt, cancelledAt, expiresAt`) plus `requiresSignIn`, `canApprove`, `currentUserId`. It does not return the token or the key id. Status precedence `cancelled > expired > approved > pending` (`board-auth.ts:49-54`).
**Approve / cancel** (`access.ts:2840-2882`) happen in the browser; the app only creates, polls and may cancel (`POST .../{id}/cancel {token}`).
**Key metadata:** `me.keyId` is the current key id when `source == "board_key"` (`access.ts:2897`); its `expiresAt` (nullable, `board-auth.ts:254`) comes from `GET /api/board-api-keys` (`access.ts:2901-2910`, fields `id,name,createdAt,lastUsedAt,revokedAt,expiresAt`).
**Revoke:** `DELETE /api/board-api-keys/{keyId}` -> `{ok, keyId}`; `POST /api/cli-auth/revoke-current` -> `{revoked, keyId}` (`access.ts:2954-2980`).

**`GET /api/health`** (`server/src/routes/health.ts`): an unauthenticated caller of an `authenticated` server gets the redacted body `{status, deploymentMode, deploymentExposure, localAiLoginSupported, commit, bootstrapStatus, bootstrapInviteActive, ...}` with NO version (`health.ts:45-51, 394-418`). `local_trusted` servers return full details to anyone. The `!db` branch omits `deploymentExposure` (`health.ts:270-290`); the 503 branch omits `deploymentMode` (`health.ts:318-330`). Hence `serverVersion` and `exposure` are nullable before pairing, and the probe fails closed: only `deploymentMode == authenticated` with status `ok` and `bootstrapStatus == ready` is accepted.

## Answers recorded in slice 1a-2 (server source, Paperclip checkout at `~/Code/Test/paperclip`)

Paths are relative to that checkout. `svc` below is `server/src/services/`.

**Feed request** (`server/src/routes/attention.ts:57-92`): `GET /api/companies/{c}/attention`, board only, query `sort` (`activity` default | `decide`), `limit` (integer 1-100, default 50; `svc/attention.ts:114-115,1924-1927`), `cursor`, `includeDismissed`, `archived`, `all` (cannot be combined with `cursor`/`limit`, `svc/attention.ts:1917-1920`), `queue`, `activitySince`, `activityUntil`. The app sends `sort=decide&limit=50[&cursor=...]`.
**Cursor paging** (`svc/attention.ts:530-546,1929-1937`): the cursor is opaque base64url JSON `{v:1, sort, id: lastItemId}`. It is bound to the sort mode, and if the item it names has left the filtered feed the server answers 400 "Attention cursor no longer matches the filtered feed". The app treats a failed cursor page as "reload from the first page". `nextCursor` is null on the last page. `totalCount`, `countsBySourceKind` and `deskBadgeCount` are computed before paging (`svc/attention.ts:1893-1901`), so they are the same on every page.
**Item and feed shape**: `packages/shared/src/types/attention.ts:221-277` (`AttentionItem`, `AttentionFeed`); detail variants `:110-187` (12 kinds, `approval, plan_approval, confirmation, questions, suggested_tasks, checkbox_confirmation, item_verdicts, failed_run, blocker, budget, agent_error, generic`).

**Q2 (ANSWERED) inline-resolvable in practice.** `inlineResolvable` per source kind: `approval` true except type `request_board_approval` (`svc/attention.ts:1159`); `issue_thread_interaction` true (`:1270`); `decision` true (`:1330`); `join_request` true (`:1395`); `failed_run` true (`:1742`); `budget_alert` true (`:1796`); `agent_error_alert` true (`:1850`); `review` true only when stalled (`:1676`); `recovery_action` false (`:1461`); `blocker_attention` false (`:1524,1576`); `productivity_review` generates no items (`types/attention.ts:14`). That set is wider than FR-033, so the app's eligibility is (server flag) AND (app-supported inline kind: `approval`, or `budget_alert` with `thresholdType = hard`) AND (role allows). Decisions open the Decision screen; everything else opens "Open in web app".
- `subject.href` is a path relative to the web app root (for example `/{prefix}/approvals/{id}`, `/{prefix}/costs`, `svc/attention.ts:1145,1773`) and nullable (an interaction on no readable issue, `:1264`). The fallback link is `baseUri + href`; with a null `href` the card shows a no-link state.
- `thresholdType` (`hard` | `soft`) is only in `subject.metadata` for budget alerts (`:1774-1782`); `detail.budget` carries `observedPercent`, `amountObserved`, `amountLimit` but not the threshold. Domain reads a typed metadata view.

**Q3 (ANSWERED) resolver audience.** The pure evaluator is `svc/issue-thread-interaction-resolution.ts:155-238`. For a board **user** it denies in exactly two cases: `addresseeUserId` is set and is not this user (`interaction_addressee_mismatch`, 403), or the policy is `not_creator` and `createdByUserId` equals this user (`interaction_creator_excluded`, 403). `human_only` and an agent addressee do not stop a human (`allow_human_override`). The feed carries `addresseeUserId` but no `createdByUserId`, so the client can evaluate only the first rule; the creator rule is left to the server's 403, mapped to `Forbidden`. Rule in the app: read-only when the role is Viewer or `addresseeUserId` names another user; "me" is `BoardAccess.profile.userId`. The audience is always shown (policy, addressee name, creator name) because the card carries facts, not copy (`types/attention.ts:189-219`).

**Q4 (ANSWERED) decision execution.** `POST /api/decisions/{id}/decide` (`routes/decisions.ts:181-186`) runs the effects inside the request (`svc/decisions.ts:675-681`, `resumeDecision`), so the response is normally already terminal. The response is the decision row plus `executions` (`svc/decisions.ts:277-281`): `{...decision, executions: [{effectIndex, effectType, targetIssueId, status, result, error, executedAt}]}`. Decision `status` is `open | decided | expired | cancelled` (`routes/decisions.ts:150`); `executionStatus` is `running | succeeded | partial | failed` or null while open (`svc/decisions.ts:667-670`: all executed = succeeded, some executed = partial, none = failed). Per-effect `status` is `claimed | executed | failed | skipped` (`svc/decisions.ts:403,424,441,483`; a changed target gives `skipped` with reason `target_changed`). Terminal = `executionStatus` in {succeeded, partial, failed}, or `status` in {expired, cancelled}. `running` appears only while another request or the recovery sweep is executing (`:571,589-607`); the sweep turns a stuck `running` into `partial` or `failed`. Polling therefore = re-`GET /api/decisions/{id}` until terminal, with a cap. Dismiss (`POST /decisions/{id}/dismiss {reason?}`, `:187-192`) either decides an option that has no effects or sets `chosenOptionId = "dismissed"` with `metadata.dismissed` (`svc/decisions.ts:733-748`).
- Errors: 409 `decision_already_resolved` and `decision_expired` carry `details.code` (`svc/decisions.ts:697-711`); 422 for `Unknown optionId`, `Input <id> is required`, `Input <id> is too long` (`:702-704`); 403 "Decision signature verification failed". Conflict -> re-read -> show the final state (acceptance 12).
- `idempotencyKey` is accepted on decide (`routes/decisions.ts:34`). A replay with the same key by the same user resumes instead of re-running (`svc/decisions.ts:690-696`). The app does not retry, but it sends a key so a manual re-tap after a timeout is safe (ADR-018).

**Q8 (ANSWERED) where `inputs` attach.** On the decision, not on the option: `decisions.inputs` (`packages/db/src/schema/decisions.ts:50`), `createSchema.inputs` (`routes/decisions.ts:27`), validators `decisionInputsSchema` (max 4, unique ids, `packages/shared/src/validators/decision.ts:89-139`). The decide body is `{optionId, inputValues: Record<string,string>, idempotencyKey?}` (`routes/decisions.ts:34`), and the server validates every input (required, `maxLength`) for whichever option is chosen (`svc/decisions.ts:703-704`). `GET /api/decisions/{id}` returns the outcome object above, so it contains `inputs`, `options`, `title`, `body`, `expiresAt`, `originAgentId`, `originIssueId`, `chosenOptionId`, `inputValues`, `metadata`, but no agent name and no `decideBy`. `decideBy` is triage data: `GET /api/companies/{c}/decision-triage/decision/{id}` (`routes/decision-queues.ts:153-163`). The Decision screen takes `originAgentName` and `decideBy` as optional hints from the feed item it was opened from; the adapter may fill them from the agent list and triage in Phase 1b. Options with a `cancel_issue_tree` effect must be `destructive` (`validators/decision.ts:103-111`); the app still checks the effect, not only the style (FR-041).

**Decision triage** (`routes/decision-queues.ts:165-186`): `PUT /api/companies/{c}/decision-triage/{sourceKind}/{sourceId}` body `{decideBy?: "today"|"this_week"|"whenever"|"YYYY-MM-DD"|null, snoozedUntil?: ISO datetime with offset | null}` (`packages/shared/src/validators/decision-queue.ts:40-48`; the date must be a real calendar date; at least one field). `sourceKind` is an attention source kind and `sourceId` is `item.subject.id` (not `item.id`). Needs `decision_triage:manage`. Response: the triage row (`svc/decision-queues.ts:767-800`).
**Inbox dismissals** (`routes/inbox-dismissals.ts:10-34,62-96`): `POST /api/companies/{c}/inbox-dismissals` body `{itemKey: "attention:..."|"approval:..."|"join:..."|"run:...", kind: "dismiss"|"snooze" (default dismiss), snoozedUntil?: ISO string}`; a snooze needs a future `snoozedUntil`, a dismiss must not have one. 201 returns the row `{companyId, userId, itemKey, kind, dismissedAt, snoozedUntil, updatedAt}` (`svc/inbox-dismissals.ts:5-35`). `DELETE .../inbox-dismissals/{itemKey}` returns 204 and is idempotent (`:98-134`); it covers dismiss and snooze alike.

**Q7 (ANSWERED) stable ids.** `item.id = "{sourceKind}:{dedupKey}"` and `item.dismissalKey = "attention:{dedupKey}"` (`svc/attention.ts:363-365,404-405`). Dedup keys: `approval:{id}`, `interaction:{id}`, `decision:{id}`, `join:{id}`, `run:{id}`, `agent_error:{id}`, `review:{id}`, `blocker:{id}`, and `budget:{policyId}:{windowStart}:{thresholdType}` (so a soft-to-hard change is a new item). Ids are unique within one instance only, so the cache is keyed by (instance, company). A dismissal stays active only while `dismissedAt >= activityAt`, a snooze while `snoozedUntil > now` (`svc/attention.ts:192-208`): new activity brings a dismissed item back. Two snooze mechanisms exist: `item.dismissal.snoozedUntil` (inbox-dismissals, used by FR-034) and `item.snoozedUntil` (triage; items hidden while in the future, `:1893`). Undo is a DELETE on the dismissal key, and the path segment contains colons, so the adapter URL-encodes it.

**Q5 (ANSWERED) budget incident resolution.** `POST /api/companies/{c}/budget-incidents/{incidentId}/resolve` (`server/src/routes/costs.ts:366-377`), body `{action: "keep_paused"|"raise_budget_and_resume", amount?: integer cents 0..2147483647, decisionNote?: string|null}`; `amount` is required for a raise (`packages/shared/src/validators/budget.ts:24-37`). Success returns the `BudgetIncident` with status `resolved` (raise) or `dismissed` (keep paused) (`svc/budgets.ts:1038-1049`). The three 422 reasons are plain `{error}` strings, no structured fields (`svc/budgets.ts:976-982`): "Resolve unpriced usage or explicitly allow it in the budget policy before resuming"; "Completed runs must finish accounting before resuming"; "New budget must exceed current observed spend". The server recomputes the observed spend at resolve time (`computeObservedSpend`, `:975`), so the app's "must exceed" check is a pre-check against `incident.amountObserved`; the server decides. Observed spend can be fractional: the column is `numeric(24,7)` (`packages/db/src/schema/budget_incidents.ts:21`), so the adapter rounds it up to whole cents (ADR-016). There is no `GET` for a single incident: `GET /api/companies/{c}/budgets/overview` returns `activeIncidents` (`costs.ts:346`, `types/budget.ts:81-88`). The sheet takes the incident from the feed item and the adapter re-reads the overview to refresh it; a resolved incident is absent from `activeIncidents`, which the app reads as "resolved elsewhere" (`NotFound`). Money is cents (`billed_cents`); no currency field exists anywhere (UI `formatCents` defaults to USD, `ui/src/lib/utils.ts:36`).

**Approvals** (`server/src/routes/approvals.ts`): `GET /api/approvals/{id}` (`:224`), `GET /api/approvals/{id}/issues` (`:287`), `GET /api/approvals/{id}/comments` (`:509`), `POST /approvals/{id}/approve|reject` body `{decisionNote?: string|null}` (`:296,412`, `packages/shared/src/validators/approval.ts:13-17`), `POST /approvals/{id}/request-revision {decisionNote?}` (`:447`), `POST /approvals/{id}/comments {body}` returns 201 the comment (`:517-543`). The server accepts a missing note everywhere; the app requires one for reject and request-revision (PRD FR-051 / FR-014 rules). Approve and reject work from `pending` **and** `revision_requested` (`server/src/lib/approval-records.ts:7,32-39`); approving an approved approval is an idempotent success (`applied:false`), but approving a rejected one is a **422** "Only pending or revision requested approvals can be approved", not a 409. Request revision only from `pending`, else 422 "Only pending approvals can request revision" (`svc/approvals.ts:87-91`). The use case therefore treats `Rejected` and `Conflict` from an approval mutation the same way: re-read and show the final state. Payloads (`ApprovalPayload.tsx`, `routes/agents.ts:4429-4433,4666-4680`): `hire_agent` {name, role, title, icon, capabilities, adapterType, reportsTo (agent id, not a name), desiredSkills[], budgetMonthlyCents}; `approve_ceo_strategy` {title, plan|description|strategy|text}; `budget_override_required` {scopeName|scopeType, windowKind, metric, budgetAmount, observedAmount, guidance}; `request_board_approval` {title, summary, recommendedAction, nextActionOnApproval, risks[], proposedComment}. Payloads are redacted by the server and every field may be missing, so each domain field is nullable.
