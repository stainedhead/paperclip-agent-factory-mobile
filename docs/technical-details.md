## The graph

`PaperclipCore` (in `shared/umbrella`) is the composition root. A platform app creates one graph and asks it for state holders.

| Call | Meaning |
|---|---|
| `PaperclipCore.createGraph(allowInsecureLocal)` | A graph on empty fakes: no factories, a `FakeClock` at 2026-11-01T12:00Z that does not advance, `FakeIdGenerator("factory-")`, a `FakeBiometrics` that **approves every prompt**, an in-memory `FakeSecretStore`, a `FakeHealthGateway` that answers "authenticated, private, ok". `allowInsecureLocal` is true only in debug builds and lets `http://localhost` and `http://10.0.2.2` through address validation. The iPhone app calls this. It is **not** a live graph: see ADR-037. |
| `PaperclipCore.createLiveGraph(allowInsecureLocal, pairingBrowser)` | The graph on the real adapters (Phase 1b-5a, ADR-067 to ADR-070). See "The live graph". |
| `PaperclipCore.createDemoGraph()` | The same wiring on fakes seeded with the demo data set of the design mocks (ADR-026). Clock frozen at Wednesday 2026-11-04T12:00Z. |

Both use an isolated Koin application, so graphs never share state. Neither can exercise the idle lock, the undo window, key expiry or "Decide now" grouping, because their clocks never advance (tests use an advanceable `FakeClock` below the graph). The "live" graph on real adapters is Phase 1b: the seam is the module that binds the ports (`portsModule()`; `demoPortsModule()` for the demo), and a build must not be released while `createGraph` still binds the fakes (ADR-037). The demo graph, the fakes and the fake demo keys ship inside the framework in every build (ADR-035).

| Member of `PaperclipGraph` | Creates / does |
|---|---|
| `createFirstRunStateHolder()`, `createAppStateHolder()` (also attaches the holder to `lifecycle`), `createFactoriesStateHolder()`, `createManageFactoriesStateHolder()`, `createSettingsStateHolder()`, `createEditInstanceStateHolder(instanceId: String?)` | Setup screens (15, app shell, 8, 16, 13, 9). `null` adds a factory. |
| `attention` | `createInboxStateHolder`, `createDecisionStateHolder(…, hints: DecisionHints)`, `createApprovalStateHolder`, `createBudgetIncidentStateHolder` (screens 1, 2, 3, 12) |
| `work` | `createWorkListStateHolder`, `createIssueStateHolder` (10, 4) |
| `agents` | `createAgentsStateHolder`, `createAgentDetailStateHolder` (6, 11) |
| `runs` | `createRunViewerStateHolder` (7) |
| `factory` | `createFactoryHomeStateHolder` (5) |
| `refresh` | `start(target: RefreshTarget): RefreshSession`; call `stop()` when the screen goes away |
| `lifecycle` | `AppLifecycleBridge`: `setForeground(Boolean)` (one call per scene change: stops or resumes refreshing and reports `WentToBackground` / `CameToForeground` to the app lock of the holder from `createAppStateHolder()`), the same calls spelled `enterBackground()` / `enterForeground()`, and `isForeground` |

Each `create...StateHolder` call returns a new holder with its own `CoroutineScope` on `Dispatchers.Default`; the screen owns it and calls `close()` when it goes away. Holders expose `state: StateFlow<XState>` and `onIntent(XIntent)`; ten of them also expose `refreshTarget`.

`PaperclipGraph.resolve<T>()` is `internal`: only code inside `shared/umbrella` can reach the fakes behind the graph (for example the `FakeLiveEvents`). To script a fake from outside, build the use cases and fakes yourself (see [usage-examples.md](../user-docs/usage-examples.md)).

## The live graph (Phase 1b-5a)

`createLiveGraph` builds the same `PaperclipGraph` surface as the demo graph (`attention`, `work`, `agents`, `runs`, `factory`, `refresh`, `lifecycle` and the `create...StateHolder` calls) on the real adapters. It reuses `useCaseModule` and `presentationModule` unchanged; only the ports module differs.

- **Seam.** `LivePlatform` (internal, `umbrella/LivePlatform.kt`) is what the graph cannot create itself: `Clock`, `IdGenerator`, `DeviceTimeZone`, `SecretStore`, `Biometrics`, `Connectivity`, the `PaperclipPersistence` and the HTTP client factory, plus `release()`. It is internal because it carries database and Ktor types that must not reach the Swift header. `PaperclipCore.createLiveGraph(allowInsecureLocal, pairingBrowser)` uses `defaultLivePlatform()` (`expect`/`actual`); an internal overload takes an explicit platform (tests, and `LiveIosGraph`). ADR-067.
- **Wiring** (`LiveModules.kt`): the nine company gateway adapters are bound under `RawPort` and wrapped by the same `SignedOutAware` decorators as the demo graph (`guardedGateways()`); `HealthGatewayAdapter` and `AuthGatewayAdapter` share one `PaperclipHttpClient`; `InstanceRepository`, `AppSettingsStore` and `AttentionCache` come from `PaperclipPersistence`. `LiveEvents` is "polling only" (the pinned server refuses board keys on the WebSocket), so screens refresh on the timer and on coming back online or to the foreground (ADR-068). No file named `Live*.kt` may import `shared.testing` or call `portsModule`, `demoPortsModule`, `sliceThreePorts` or `signalPorts` (`LiveWiringRulesTest`, with a self-test); `LiveGraphTest` resolves ports from a live graph and checks none is a fake.
- **First launch (AD-041).** Nothing is seeded. An empty database yields an empty factory list and the first-run flow.
- **Destinations.** Adapters read the factory's address, pins and key from the repository for every call (`StoredCredentials`), so an address saved by Edit factory is the next call's destination. `allowInsecureLocal` is enforced in the client as well as in address validation: a stored `http` address of a release graph fails with `CertificateInvalid` before any request.
- **Lifecycle.** `PaperclipGraph.close()` is idempotent and releases, in order, the HTTP client (and the engine under it; Ktor does not close an engine it was handed, so `PaperclipHttpClient.close()` does), the database, then the platform (the iOS network monitor). Close the screens' state holders first.
- **Platforms (ADR-069).** iOS: `IosLivePlatform` = `KeychainSecretStore`, `LocalAuthenticationBiometrics`, `NwConnectivity`, `SystemClock`, `UuidIdGenerator`, `SystemDeviceTimeZone`, and `openIosPersistence` (default `Application Support/PaperclipData`, excluded from backups, file protection). `LiveIosGraph.createLiveGraph(allowInsecureLocal, pairingBrowser, IosLiveSettings(keychainService, dataDirectory, unlockReason, confirmReason))` chooses the folder, Keychain service and localized prompt texts; the two-argument `PaperclipCore.createLiveGraph` uses the app service, the default folder and English texts. JVM: `UnavailableSecretStore`, `UnavailableBiometrics`, `OptimisticConnectivity`, in-memory database: pairing and destructive actions fail closed. Android (ADR-124): `AndroidLivePlatform` = `KeystoreSecretStore` (its prompt callback is `BiometricPromptBiometrics.authenticateWithText`), `BiometricPromptBiometrics` on the process-wide `AndroidAuthHost`, `ConnectivityManagerConnectivity` (closed by `release()`), `SystemClock`, `UuidIdGenerator`, `SystemDeviceTimeZone`, `openAndroidPersistence` (database opened first, network monitor last) and the shared OkHttp client. `AndroidLiveGraph.openLiveGraph(context, allowInsecureLocal, pairingBrowser, AndroidLiveSettings(unlockReason, confirmReason, writeReason, keyAliasPrefix))` returns `AndroidGraphOpen.Opened(graph)` or `Unavailable(cause)` and leaves nothing open on failure. The context-free `PaperclipCore.createLiveGraph` still throws `IllegalStateException`, naming `AndroidLiveGraph.openLiveGraph`.
- **Pairing browser (ADR-070).** The port is a Kotlin suspend interface and `Secret.reveal()` is hidden from Swift, so the app passes `PairingBrowsers.shared.fromCallback { url, finished in ... }` (`CallbackPairingBrowser` in `infrastructure/api`, the only reveal point). The callback gets the approval address as text, opens it in `ASWebAuthenticationSession`, and calls `finished()` when the page is dismissed.
- **Launch surface for Swift (F-B-5, F-B-8, F-B-9, ADR-084).** `createLiveGraph` (both forms) is unchanged and aborts the process when graph construction throws. New: `PaperclipCore.shared.openLiveGraph(allowInsecureLocal:pairingBrowser:)` and `LiveIosGraph.shared.openLiveGraph(allowInsecureLocal:pairingBrowser:settings:)` are `@Throws(Exception::class)`, so Swift sees `throws` and can show a retry screen (`StorageUnavailableException`, an unusable data folder, a Keychain that cannot open); nothing is left open when they throw. `PairingBrowsers.shared.onMainThread(show:dismiss:)` runs both closures on the main thread and calls `dismiss` when the pairing is cancelled; `fromCallback` keeps its signature and runs `show` on a background dispatcher. Use one live graph per process. The app target declares `NSFaceIDUsageDescription` in `iosApp/project.yml` (English text; there is no localized InfoPlist yet) and `InfoPlistTests` checks the generated plist.
- **How the iPhone app switches.** In `PaperclipApp`, replace `PaperclipCore.shared.createGraph(allowInsecureLocal:)` with `PaperclipCore.shared.createLiveGraph(allowInsecureLocal:pairingBrowser:)` (or `LiveIosGraph` for its own folder and localized prompts), keep one graph for the whole process (`close()` is for tests and for tearing a graph down), and keep `createDemoGraph()` for the explicit demo option.
- **Tests.** JVM (`shared/umbrella/src/jvmTest`): `LiveGraphTest`, `LiveFlowsTest`, `LiveRefreshTest`, `LiveDefaultsTest` drive state holders against `StubPaperclipServer` (its source files are copied into the test compilation by the `sharedStubSources` task, ADR-067) on a real SQLite file. Android host: `LiveAndroidDefaultsTest`, `AndroidLiveGraphTest` (Unavailable leaves nothing open), `AndroidLivePlatformTest`, `AndroidLiveSettingsTest`, `ResumedReferenceTest`; emulator: `AndroidLiveGraphDeviceTest` (the real graph reaches the empty first-run state, device ports are real, release unregisters the monitor, a release graph refuses a stored `http` address). iOS simulator: `LiveIosGraphTest` (database folder, backup exclusion, first run). Swift Testing in the app host: `LiveGraphInteropTests` (every state holder; a real health probe through URLSession to a loopback server, `local_trusted` refused). The Darwin engine and the Keychain are never driven by a pairing flow in a test; the real server is never contacted (CI container only).
- **Size.** Linking the adapters into `PaperclipKit` grew the debug framework binaries from 25.9 MB (simulator) and 25.7 MB (device) to 32.8 MB and 32.6 MB (+6.9 MB, +27%); the umbrella binaries link `-lsqlite3`.

## Mutation use cases: the fixed order

Every mutation takes a `CompanyContext(scope, role, userId)` and runs in this order (ADR-019, ADR-021):

1. **Permission.** `Permissions.allows(role, action)`; otherwise `MutationResult.Denied`. A viewer never reaches a gateway. Device-local actions (add, edit, remove, sign out, revoke key, settings) are open to every role.
2. **Validation.** Required notes and bodies, input values, status preconditions, snooze time in the future, interaction answers. Failure returns `Invalid(reason)`.
3. **Device authentication.** Only if `DeviceAuthPolicy.requires(action)`: pause agent, cancel run, reject approval, destructive decision option, raise-and-resume of a budget, remove factory. `DeviceAuthGuard` calls the `Biometrics` port; anything but `Approved` returns `NotAuthorized(result)`. There is no setting that turns this off.
4. **One gateway call.** Never retried. A decision carries an idempotency key from `IdGenerator`. `DecideDecision` takes the `DecisionId` and re-reads the decision before step 3, so destructiveness and "still open" come from the server's copy, not the caller's (ADR-032). A decision that is no longer open returns `Reconciled(Conflict, current)` with no gateway call.
5. **One re-read** only after `Timeout` or `Conflict`: the result is `Reconciled(error, current)` with the entity as the server has it now. If the re-read also fails the original error is returned as `Failed`. Run now (`InvokeHeartbeat`) and the issue and approval comments read the live runs or the comments *before* the call and compare after a timeout: `Reconciled` only for a new run or the person's own new comment, otherwise `MutationResult.Unknown(error)` ("the call may or may not have happened", ADR-032). The screen reloads and shows `FeedbackKind.Unknown`; it never claims success or "skipped".

`MutationResult` is `Done`, `Denied`, `Invalid`, `NotAuthorized`, `Failed`, `Reconciled` or `Unknown`. `Denied`, `Invalid` and `NotAuthorized` mean no gateway call happened. Offline gating is the state holders' job (the use cases have no `Connectivity`): offline, every action is disabled with `ActionsDisabledReason.Offline`.

Reads go through `retryingRead`: up to three retries with 500 ms, 1 s and 2 s backoff, only for `Unreachable`, `Timeout` and `ServerError`, so a persistent failure of one read makes four calls. A use case with several reads (`LoadApproval`, `LoadIssue`, `LoadInstanceAccess`) shares one `RetryBudget` of 3.5 s across all of them and stops retrying at once when `Connectivity` says offline. `CertificateInvalid` is never retried (ADR-034).

Configuration and credential changes of one factory (`UpdateInstance`, `KeyEnrollment`, the local half of sign out and remove, `SignedOutMarker`) run under a per-factory `InstanceLocks` mutex, never held across a server call (ADR-033). A key is validated against the host it was issued for before it is stored; a failed or cancelled enrollment leaves no orphan secret, and sign out deletes the local credentials even when cancelled (`NonCancellable`).

## Error taxonomy

| Layer | Type | Values |
|---|---|---|
| Domain | `DomainError` | `Unreachable`, `CertificateInvalid`, `Timeout`, `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, `Rejected(reason)`, `ServerError`, `RateLimited`, `Malformed`. Failures are values (`DomainResult.Failure`), never thrown. |
| Application | `MutationResult`, `RevokeKeyResult`, `InvalidInput` | see above; `RevokeKeyResult.CurrentKeyUnknown` means this phone does not know which server key is its own, so it will not revoke any (nothing is sent); `InvalidInput` is `NoteRequired`, `BodyRequired`, `WrongStatus`, `UnknownOption`, `SnoozeNotInFuture`, `UndoWindowClosed`, `TitleRequired`, `NotAddressedToYou`, `Answer`, `Input`, `Amount` |
| Application | `BaseUriError`, `ProbeRefusal`, `InstanceNameIssue` | address, server-mode and name problems when adding or editing a factory |
| Presentation | `ErrorKey` | `Unreachable`, `CertificateInvalid`, `Timeout`, `SignedOut` (from `Unauthorized`), `NoPermission` (from `Forbidden`), `NotFound`, `Conflict`, `Rejected` (with the server's reason as `detail`), `ServerError`, `RateLimited`, `Malformed`, and the sign-in keys `InvalidKey`, `StorageFailed`, `CurrentKeyUnknown` |
| Presentation | `DeviceAuthIssue`, `AddressIssue` (includes `InvalidPath`), `ActionsDisabledReason` (`Offline`, `ViewerRole`, `OwnerRole`) | |

A 401 from any company-scoped call marks the factory Signed out through `SignedOutAware<X>Gateway` decorators bound by the umbrella (ADR-031). **Phase 1b adapter obligations:** map HTTP 401 to `DomainError.Unauthorized` (so the decorators see it), HTTP 429 to `DomainError.RateLimited` (pairing tolerates it while waiting, ADR-034's budget applies to reads), and TLS or name-verification failures to `DomainError.CertificateInvalid` (plain connection failures stay `Unreachable`).

A 403 means the role may have changed: after a mutation *or a read* answers `Forbidden`, the holder resolves the role once more (no loop, the mutation is not repeated) and re-renders with the new role's actions; any other error leaves the role alone.

`BaseUri` (FR-003) also refuses a path with whitespace, control characters, a backslash, an empty or `.`/`..` segment (also percent-encoded) or a malformed `%` escape (`BaseUriError.InvalidPath`), and a host with an empty or over-long label, a leading or trailing hyphen, a trailing dot, non-ASCII characters (paste punycode), a non-canonical IPv4 literal or a malformed bracketed IPv6 literal (`InvalidHost`).

All text a screen shows is a key; the platform UI owns the wording and the localisation. Raw server JSON never crosses the adapter boundary.

## Refresh policy

`RefreshVisibleScreen(connectivity, lifecycle, liveEvents)(scope, target)` returns a `RefreshSession` (ADR-027). The platform passes a holder's `refreshTarget` to `graph.refresh.start` when the screen appears and calls `session.stop()` when it goes away.

- Active only when the phone is online **and** the app is in the foreground.
- While active, refreshes every `target.refreshIntervalSeconds`. The interval is part of each holder's state, so it can change: 15 s by default; 5 s on the Run viewer while the run is live and on Agent detail while the agent has a run; 0 (no timer) for a finished run, a final Decision, a resolved Approval and a closed Budget incident.
- Refreshes at once when the app returns to the foreground or the phone comes back online (not at start: the holder has just loaded).
- Refreshes when a `LiveEvent` maps, through `InvalidationRules`, to something the target says it is affected by (`agent.status`, `heartbeat.run.*`, `activity.logged`), at most once a second, newer events replacing older ones. There is no real `LiveEvents` adapter yet, so this path only runs with a fake.
- Timers use coroutine `delay`, not the `Clock` port, so tests run in virtual time.
- The state holders ignore a `Refresh` while one is in flight, so the policy cannot double-load.
- Nothing refreshes in the background or offline. The shell reports the background with one call, `graph.lifecycle.setForeground(Boolean)`, which also tells the app lock (`WentToBackground` / `CameToForeground`) of the holder made by `createAppStateHolder()`. A shell that never created one has no lock to tell.

The Inbox is cache-first (ADR-017): `LoadInbox` emits the cached first page (marked `isFromCache`), then the network result; the label "Updated" is the server's `generatedAt`. Only the first page is cached.

### Swift-facing rules

The Swift interop review (acceptance criterion 6, in the spec's implementation notes) found these rules, several enforced by Konsist:

- No generics, `Result`, or Kotlin default arguments on the presentation and umbrella surface; Swift passes every argument.
- No function or property named `new…`, `alloc…`, `copy…`, `mutableCopy…`, `init…` (Kotlin/Native would rename it, for example `newFoo` to `doNewFoo`); factory methods are `create…` (ADR-009).
- UI text is keys (enums); never prose.
- A state holder is `state` (an `AsyncSequence` through SKIE, and `.value` for the current state), `onIntent(intent:)` and `close()`. Intents are `data object` (`FactoriesIntentRefresh.shared`) or `data class` (`InboxIntentFilterSelected(kind:)`).
- Create and use a holder on the main actor; never pass one to another actor. The holders load on their own dispatcher, so a test waits for a settled state instead of asserting a loading phase.
- Nullable numbers arrive boxed (`KotlinInt?`, `KotlinLong?`): read `.intValue` or `.int64Value`. A `StateFlow<Boolean>` value is a `KotlinBoolean` (`.boolValue`).
- Sealed hierarchies get an `onEnum(of:)` function for exhaustive `switch`.

## The Android app (Phase 2a)

**Entry.** `PaperclipApplication` builds one `AppEnvironment` per process: an `AppGraphProvider` (`DemoGraphProvider`, `FirstRunDemoGraphProvider`, `LiveGraphProvider`) chosen from `LaunchConfiguration`, a `GraphSession` that owns the graph, the app, first-run and Inbox-badge holders and the refresh session, and the process-wide `AndroidAuthHost`. `LiveGraphProvider` calls `AndroidLiveGraph.openLiveGraph(context, allowInsecureLocal = BuildConfig.DEBUG, ...)`; an `Unavailable` result becomes a "cannot start yet" screen with Try again and never a fake graph (ADR-124, ADR-125). `MainActivity` is the only exported component, registers itself as the `AuthHost` while resumed; `FLAG_SECURE` is set on its window while the app is locked and during pairing (`shell/PrivacyShield.kt`). Screens own their holders through `HolderViewModel` (cleared with the back stack entry, kept across rotation, `HolderViewModelTest`); the Inbox holder is the session's, so the tab badge stays current while another tab is shown.

**Launch extras (debug and `releaseDemo` builds only; a shipping release ignores them).** `demo`, `demo_first_run`, `demo_biometrics` (scripted prompt answers `cancelled,failed,approved`), `demo_inbox_cards` (extra generated Inbox cards, for the frame-timing benchmark). See [configuration-reference.md](../user-docs/configuration-reference.md).

**Device services (Keystore, BiometricPrompt, connectivity)** are described under "Device services". Protected Keystore keys are authorised **per use** (`setUserAuthenticationParameters(0, STRONG | CREDENTIAL)`, API 30 and later; ADR-139, which withdrew the 5 second window of ADR-123): the backend returns an initialised unused `Cipher`, `BiometricPromptBiometrics.authenticateWithCipher` shows the prompt with it as a `CryptoObject`, and the store finishes the operation with the cipher the prompt returns, so an earlier prompt or another app's authentication never opens a protected secret and the activity still never enters `securestore`. Below API 30 a protected write fails instead of falling back to an unprotected key.

**Build types.** `debug`; `release` (R8 and resource shrinking, `Log` calls stripped, signed by the `upload` config when `PAFM_UPLOAD_STORE_FILE`, `PAFM_UPLOAD_STORE_PASSWORD`, `PAFM_UPLOAD_KEY_ALIAS` and `PAFM_UPLOAD_KEY_PASSWORD` are set, otherwise by the debug key and not a distribution artifact: `verifyReleaseSigning` runs before `packageRelease`, fails a half-set upload configuration everywhere, and fails a build with `CI` set and no upload key unless `PAFM_ALLOW_DEBUG_SIGNED_RELEASE=1`, which `android.yml` sets because its release job is a smoke build; ADR-132, R-015); `releaseDemo` (release plus the demo entry, application id suffix `.demo`, debug-signed); `benchmark` (`releaseDemo` plus a profileable manifest, suffix `.benchmark`); `nonMinified` (`benchmark` without R8, to record the baseline profile). `versionName` is the catalog's `android-app` (0.1.0); `versionCode` is `git rev-list --count HEAD`, so every checkout that builds a release must have the full history (`fetch-depth: 0` in `android.yml`); without git it falls back to 1. Permissions: exactly `INTERNET`, `ACCESS_NETWORK_STATE` and `USE_BIOMETRIC` (`AndroidManifestRulesTest` on the merged manifests of three build types; `scripts/android-release-smoke.sh` repeats it on the APK with `aapt2`). `allowBackup=false`, data-extraction rules exclude everything, `usesCleartextTraffic=false`, `android:enableOnBackInvokedCallback="true"` (predictive back is on by the manifest and not by the platform default at targetSdk 36; `AndroidManifestRulesTest` checks every variant); the debug source set alone adds a network security config that allows cleartext to `localhost` and `10.0.2.2`.

**Test stack.** `androidApp/src/test`: JUnit 4 with Robolectric 4.17 (API 36; there is no API 37 Robolectric jar) for Compose UI tests and Roborazzi, and JUnit 5 for pure tests, both on the one `testDebugUnitTest` task through the Vintage engine (ADR-121). `shared/**` stays on kotlin.test. `androidTest` runs under the Android Test Orchestrator on a device. Method names in `androidTest` and `androidDeviceTest` are camelCase (DEX 039).

**Scripts** (all need `adb` and a running device): `android-release-smoke.sh live|demo`, `android-live-smoke.sh` (no server needed), `android-live-pairing.sh` (needs Docker; written and never run; re-read in Group 5, `bash -n` passes, no bug was provable without a run), `run-benchmarks.sh`, `generate-baseline-profile.sh`.

## Work list and Issue on Android (2a-7)

`WorkListScreen` is the Work tab root (waits for the selected factory and company like Factory home; its holder is keyed by session, factory and company, so filters and search survive tab switches and never leak between factories) and `IssueScreen` is the pushed `AppRoute.Issue` (reached from the Work list, a subtask or related-issue link, the Inbox, Agent detail and the Run viewer; its holder is keyed by the route's id). Each is a thin function over a stateless `WorkListContent` / `IssueContent(state, send, ...)`, and `AppTabs` now has no placeholder: both `when` blocks are exhaustive over the tabs and routes. The iPhone split is kept: the holder says which filters exist, what a search matches, who may create, comment, reopen, interrupt, change status or assign, which statuses and assignees are offered, and whether an answer is complete; Compose lays it out.

- **Text stays in the screen.** The search box, the comment (with its reopen and interrupt switches), the title of a new issue or subtask, the answers, the free-text "something else" and every reason are `rememberSaveable` fields that only send change intents; the holder renders asynchronously and showing its state back into a field would drop characters (ADR-108, ADR-131). Search is sent when the person submits it (IME search); clearing the box sends an empty search at once. The comment box is cleared only when `commentSentCount` changes, so a refused or failed comment (`BodyRequired`, a timeout, a 500) comes back into the box with the reason in the banner; a New issue or subtask sheet closes on `createdIssueId` / `subtaskCreatedCount` and keeps what was typed on a failure, and the outcome is shown inside the open sheet rather than twice.
- **Thread and interactions.** Comments and request cards are one list in time order, as the holder gives it. `InteractionCard` draws the five kinds (suggested tasks, questions with single or multiple choice and "something else", a confirmation, checkbox options, verdicts per item with a reason) and forwards `InteractionChoiceToggled`, `InteractionTextChanged`, `InteractionVerdictChosen`, `InteractionPrimaryTapped` and `InteractionRejectTapped`; the main button is enabled only while the card's `submitIssue` is null and the reject button while `rejectIssue` is null, and the text under the button is the shared `InvalidKey`. Read-only reasons (handled, someone else's, blocked, viewer, offline, unsupported) are the card's. No device-owner prompt is added: none of these answers is on the AGENTS.md destructive list.
- **Kinds the app does not answer.** `connection_intent` and unknown kinds show their reason and "Open in the web app". The address is the instance's issue page the holder supplies (`openInWebUrl`); `WebOpener` refuses anything that is not `https` (`acceptablePage(url, allowsInsecureLocal = false)`, so also `http://localhost` and every other scheme) before the system is asked, opens a Custom Tab (else the browser) with no header, extra or token, and the card says so when nothing opened.
- **Files are listed, not opened.** The brief asks for the system viewer through the shared ranged read. `IssueGatewayAdapter.attachmentContent` is adapter-only (ADR-064); no port exposes it, so the app cannot reach it without importing `infrastructure.api`, which Konsist forbids. The Files tab therefore lists name, type and size and says that files cannot be opened in the app yet. This is reported as a shared-core gap (a port such as `IssueAttachments.read(scope, issueId, attachmentId, range)`).
- **Rows read as one sentence.** A Work row and a subtask are one 48 dp target whose children are cleared and replaced by "PAP-1204. Add retries to webhook ingest. Blocked · High · Engineer 1" (the iPhone's accessibility label); nested merge boundaries (pills, selectable choices) do not merge into a parent's text, so the sentence is set explicitly.
- **Tests.** `WorkListScreenTest` (every saved filter against the demo's server rules, search on submit and clear, a row opens its issue, a blank title refused, a created issue opened, offline), `WorkListVariantsTest` (viewer, failed read, paging, failed create keeps the title), `IssueScreenTest` (PAP-1204 and PAP-1182: header, comments in order with who and when, Plan, Runs with count, Files, a subtask and a parent link, comment sent and box cleared, refused comment kept, reopen and interrupt switches, status menu, reassign, add subtask, offline), `IssueVariantsTest` (viewer, failed comment comes back, box clears only when the count moves, switches sent with the comment, failed read and failed tab), `InteractionCardTest` (all five kinds, the unsupported kind with https and http addresses, viewer, offline, handled, busy), `InteractionFlowTest` (main PRD acceptance criterion 7 on the demo graph: the two questions validated one at a time, a typed answer in place of an option, send, card Answered, and the question gone from the Inbox feed through the demo `onAnswered` hook), `WebOpenerTest`, `WorkPresentationTest`, `WorkLargeTextTest` (named actions displayed and at least 48 dp tall at font scale 2.0) and `WorkScreenshotTest` (Work and Issue in light, dark and font scale 2.0). ## Known limitations and gaps

Behaviour:

1. **Live events.** `LiveEvents` has no real adapter (board keys fail on the WebSocket); screens refresh by polling.
2. **Budget history.** A budget incident that has left the server's active list cannot be told apart as resolved or dismissed, because the overview lists only open incidents (ADR-029, research B1). The screen shows `NoLongerActive`; `KeptPaused` and `Raised` come from the app's own resolve response.
3. **Demo fakes.** They ignore the company id, so Side Project Co shows the Acme Labs data. The demo Run viewer's events and log are the same for every run.
4. **Decision details.** `GET /decisions/{id}` has neither `decideBy` nor the agent name; the Decision screen receives them as hints from the Inbox card (ADR-018). Opened from anywhere else it shows neither, and no Snooze (ADR-025).
5. **Priority filter.** "Critical and high" is filtered on the device, so a page can hold fewer rows than the page size (ADR-022).

Android (Phase 2a; each item is also in `specs/archive/261104-phase-2a-android-ui/status.md`, whose "R-009 evidence record" table has one row per unproven item, and the commands are in [android-verification-checklist.md](./android-verification-checklist.md)):

6. **Frame budget not met on the emulator.** The 200-card Inbox fling on the Pixel_9_Pro emulator (API 37, arm64, host GPU), after the benchmark was changed to wait for the content, had 52.4% of 2524 frames over their deadline (CPU P50 9.1 ms, P90 34.1 ms). After the R-008 fixes (one shared clock, late-read ages, stable card parameters, lighter swipe and card drawing) it had 40.7% of 2533 frames over their deadline (CPU P50 7.8 ms, P90 25.9 ms) against a budget of 5%: better, still not met. An emulator says little about a phone, so the item stays open for a Pixel 6 run. Cold start to the Inbox with content was 315 ms median of 10 (budget 1.5 s), emulator only. The nightly `benchmark` job has not run on GitHub.
7. **Unproven on a device.** A pairing against the pinned server (`scripts/android-live-pairing.sh` was never run: no Docker daemon); new-fingerprint invalidation of the Keystore key (the two phase tests skip without an orchestrated lock-screen change); the system `BiometricPrompt` on a destructive action with enrolled credentials, and that another app's authentication a moment earlier does not satisfy a protected read (per-use authorisation, ADR-139: only the key parameters and the refusal of an old key are device tests); StrongBox (no shipped test reports where a key lives); a manual Pixel and Samsung pass; TalkBack (accessibility is audited from the semantics tree only, ADR-134, and the live regions and field semantics of R-025 and R-026 are asserted, not heard); `FLAG_SECURE`, Recents and predictive back on API 28 and 33 (Robolectric only; the emulator check was API 37).
8. **`android.yml` has not run on the hosted runners.** It uses the tasks that passed locally; the local emulator was API 37 arm64, CI's is API 34 x86_64.
9. **Shared-core gaps that the Android UI reports rather than works around:** no port for attachment bytes (files are listed, not opened); no `isRefreshing` on the Agents, Run viewer, Issue and Work states (no pull-to-refresh spinner there); no Viewer membership in the demo data, so viewer variants are built states; `DemoControls` exposes only the prompt count, so some "nothing was sent" proofs read the screen instead of a call counter; the demo graph binds `FakePairingBrowser`, so the Custom Tab launch is proven by `CustomTabsPairingBrowserTest` and `PairingRoutingTest`, not end to end.
10. **Not rendered on Android:** inline markdown in comments and plans. Not ported: the iPhone's factory switcher line on screen headers.
11. **Placeholder art.** The adaptive launcher icon and splash are placeholders (ADR-133).
12. **OPEN OWNER DECISION: prompts per refresh with app lock on (ADR-144, not implemented).** With app lock on, the board token is a protected secret, `StoredCredentials.call` reads it for every gateway call, and since ADR-139 every protected read is its own system prompt. A refresh that makes several calls therefore asks for the fingerprint several times, and the 15 second timer repeats it; the count per screen has not been measured (checklist item 4). The choice is between (A) keeping per-call authorisation, which is the strongest and probably unusable with auto-refresh, (B) one authorisation per refresh, read once into memory for that refresh only, and (C) a short in-memory token for the foreground unlock session, best for usability but with the token in process memory for that time while destructive actions still ask. It trades INTENT principle 1 (security over convenience) against usability; until the owner decides, the code stays at (A).
13. **Attachments cannot be opened on either platform.** The design (a gateway port, an app-private cache that is never named by a secret, a `FileProvider` share on Android and QuickLook on iOS, two follow-up pull requests, shared first) is ADR-143; no code was written in this phase. The follow-up work items are listed in the review spec's `status.md`; they are not filed as GitHub issues.
14. **Tests that name a gap.** No Android test asserts that the next factory becomes active after a removal, that a renamed device keeps the old name on old keys, or that the `local_trusted` refusal text is rendered (archived Android spec `status.md`, acceptance mapping).

Model gaps (the design mocks show these; the model has no field, so the demo state does not):

- An agent's next heartbeat time (not in the server's agent list).
- The network label such as "Tailscale" (derivable from the `.ts.net` host; a UI concern).
- The Approval screen carries `reportsToAgentId`, not the name; a name join is deferred.
- Settings "Each factory" has status and expiry but not the default company name; Manage factories has no company count; Edit factory shows the days left but not the key tail (the key id is in Settings, Paired devices and keys).

Swift surface (deferred, with reasons, in the review fix spec): nullable numbers arrive boxed (29 `Int?` or `Long?` properties in the presentation sources at the last count; no cheap SKIE option); every holder and state exposes a public initialiser, so Swift could build one outside the graph (the graph is the supported path; intents must stay constructible from Swift); a data class `copy` is exported as `doCopy`; a few state types expose domain enums (`IdlePeriod`, `Exposure`, `ProbeRefusal`, `InstanceNameIssue`) instead of UI twins (no Swift screen consumes them yet); `ErrorUi.detail` carries the server's own reason string, which cannot be localised. The `description` collision is fixed (`summary`).

Process:

- The infrastructure Konsist rule scans every `src/<set>Main` of every module; it checks nothing on the real tree while the infrastructure modules have no sources, and a fixture test proves it reports a violation once they have.
- TDD evidence is self-reported: commit history cannot show a red run, so red evidence is recorded in the commit bodies and in the review fix spec's implementation notes.
- Slice 1a-1 application and presentation code was written in the same pass as its tests (domain was strictly test first); recorded as a process deviation in the spec's implementation notes.
- The first-run and edit probe and pair job fields are plain (non-atomic) fields written from the UI thread; a lost write is bounded by the address binding of the probe result (ADR-030).
- "Continue to pairing" in the iPhone shell is enabled for a valid address and does nothing; the shell is a walking skeleton and this is stated in the user docs.

## Persistence (Phase 1b-2)

- Schema: `src/commonMain/sqldelight/.../db/*.sq` and `1.sqm` (version 2). `1.db` and `2.db` are committed snapshots checked by `verifyCommonMainPaperclipDatabaseMigration` in `check`. A change to a `.sq` file needs a new `N.sqm`, a regenerated snapshot (`generateCommonMainPaperclipDatabaseSchema`) and a migration test.
- One database per app; the three SQL adapters share one serial dispatcher (ADR-043). `PaperclipPersistence.recreated` tells whether an unusable file was replaced by an empty one (ADR-042); a `paperclip.db.sweep-pending` marker file, written before the wipe and removed only after `SweepOrphanSecrets` completed, keeps that true across a failed reopen or a kill (ADR-085). `BaseUri` drops the default port, so one address has one spelling (ADR-087).
- Files: iOS `Application Support/PaperclipData/paperclip.db` (folder and files excluded from backup), Android `noBackupFilesDir/paperclip.db` (plus `paperclip.db.sweep-pending`), JVM a given file or memory. On Android the framework's own reaction to an unreadable file (delete it and silently open an empty one, then retry) is switched off (`KeepCorruptFileCallback.onCorruption` does nothing), so `openRecovering` sees the failure, sets the sweep marker and wipes; `AndroidPersistenceDeviceTest` (emulator) proved the framework default skipped the marker and the secret sweep.
- Tests: the existing `InstanceRepository`, `AppSettingsStore` and `AttentionCache` contract suites run against the SQL adapters on the JVM, the Android host test (JDBC driver) and the iOS simulator (native driver, temp file), plus tests for mapping, migration, recovery, concurrency, secrets and (iOS) backup exclusion. The Android driver factory is exercised on an emulator by `AndroidPersistenceDeviceTest` (corrupt-file recovery, sweep marker, no secrets in the file).


## Device services (Phase 1b-3)

- **Keychain** (`securestore`, iosMain): generic password items, service = a fixed id, account = `instance/{id}/{name}`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, `kSecAttrSynchronizable = false` on every query. `requireUserPresence` stores behind `.biometryCurrentSet`, else `.userPresence`, else the write fails (never open). A protected write adds a `{account}#protected` marker so a vanished protected item reads as `Invalidated`. Read failures other than not found are `Denied`; writes `Stored`/`Failed`; refused deletes throw. `deleteNamespace` lists accounts by attributes only. ADR-051. `KeychainWriter` holds the write side, `KeychainBackend` is the seam tests script, `SecurityKeychain` is the real backend.
- **Testing**: the store's decisions and the shared `SecretStoreContract` run in `iosSimulatorArm64Test` on a scripted backend. The real Keychain needs entitlements, so `iosApp/Tests/iosAppTests/KeychainSecretStoreTests.swift` runs inside the app test host through `PlatformServices` (umbrella `iosMain`), which also runs the contract on the real Keychain. `scripts/ios-test.sh` signs ad hoc. ADR-050.
- **Biometrics**: `LocalAuthenticationBiometrics` over an internal `DeviceAuthenticator` (`LAContextAuthenticator`: new `LAContext` per prompt, `LAPolicyDeviceOwnerAuthentication`). ADR-052 has the code mapping; no passcode means Unavailable (fail closed).
- **Connectivity**: `NwConnectivity` over `PathSource` (`nw_path_monitor` on its own serial queue), online until the first path, `close()` cancels. The foreground flag is still the umbrella's `AppLifecycleBridge`, driven by the app.
- **Keystore** (`securestore`, androidMain, AND-001, ADR-123): one record file per secret path in `noBackupFilesDir/secrets` (file name = percent-encoded path, so `namespaces()` lists names without a `Cipher`), format magic + protection flag + IV + AES-256-GCM ciphertext, the path as associated data. `RecordFiles` writes a temp file, syncs and renames atomically, all calls under one mutex. `AndroidKeystoreBackend` makes non-exportable AES-256 keys (StrongBox first, `StrongBoxUnavailableException` falls back to the TEE; a protected key is `setUserAuthenticationRequired` with per-use authorisation (validity 0, `CryptoObject`, ADR-139), needs API 30 and a lock screen, else the write fails: never unprotected; a key from the old 5 s design reads as `Invalidated`). One key per secret and mode (`path:u` / `path:p`). Read mapping: ok = `Found`; no key, bad tag, truncated or corrupt record = `Missing`; `KeyPermanentlyInvalidatedException` or `UnrecoverableKeyException` (ADR-139, R-010) = `Invalidated`, any other `GeneralSecurityException` from loading the key = `Denied`; a refused prompt or any other Keystore failure = `Denied`. Write failures = `Failed` and leave the old record. `KeystoreSecretStore(context, authenticate, writeReason)` takes the device-owner prompt as a function `(reason, Cipher) -> Cipher?`; the app wires it in 2a-2.
- **BiometricPrompt** (`platform`, androidMain, AND-002, ADR-123): `BiometricPromptBiometrics(host: AuthHost, reasons: ReasonTexts)` over an internal `PromptLauncher` (`ActivityPromptLauncher` shows the real `BiometricPrompt`). `AuthHost.current()` is the resumed `FragmentActivity` the app registers; `null` (background) is `Unavailable`. Authenticators: strong biometrics or device credential on API 30+, weak biometrics or device credential on API 28 and 29 (the library rejects the strong combination there). `canAuthenticate` is asked first, so nothing enrolled and no credential is `Unavailable`. Codes: user cancel, negative button, canceled = `Cancelled`; lockout, permanent lockout = `LockedOut`; hardware unavailable or absent, none enrolled, no credential, security update = `Unavailable`; the rest, and any unknown code = `Failed`. `ReasonTexts` moved to commonMain and is shared with iOS.
- **ConnectivityManager** (`platform`, androidMain, AND-003): `ConnectivityManagerConnectivity(context)` over an internal `NetworkMonitor` (`SystemNetworkMonitor`: `registerDefaultNetworkCallback`). The first value is read from the active network before the callback; online means `NET_CAPABILITY_INTERNET`, validated or not (DEC-2, ADR-142: a LAN, split-DNS, captive or VPN path whose probe fails is "online, unknown" and the real request decides); `onLost` and `onUnavailable` are offline; a refused registration (`SecurityException`, `IllegalStateException`) leaves it offline; `close()` unregisters once and later callbacks are ignored. Needs `ACCESS_NETWORK_STATE` (the app declares it).
- **Android and JVM**: `UnavailableSecretStore`, `UnavailableBiometrics` (never approve, never store), `OptimisticConnectivity`. System clock, UUID ids and the device zone are common code. ADR-053.
- **Key invalidation: what is verified and what is not (F-B-7, ADR-083).** The store maps only `errSecItemNotFound` plus the surviving `#protected` marker to `Invalidated`; `errSecAuthFailed`, `errSecInteractionNotAllowed`, `errSecUserCanceled` and `errSecNotAvailable` are `Denied` (retry, nothing is deleted). Verified on the simulator (scripted backend, `KeychainSecretStoreTest`, and the real Keychain in `KeychainSecretStoreTests.swift`): the mapping, the marker rules, the replace-then-delete order, the delete order (marker first), and that an authentication failure on a protected item stays `Denied`. **Not verified on a device**: that iOS answers a read after a biometric-set change with `errSecItemNotFound` (the whole re-pair path assumes it), that a Face ID prompt really appears (the plist key is there since F-B-9, the simulator has no Face ID), and that a passcode change keeps the item. Manual device check, to be recorded in `status.md`: (1) pair a factory with Face ID on a test iPhone; (2) kill and relaunch, read works after the prompt; (3) Settings, Face ID and Passcode, reset Face ID and enrol again; (4) open the app: it must say the key was invalidated and offer pairing, not "denied" in a loop; (5) cancel the prompt: it must say denied and keep the key; (6) change the passcode only: the key must still work. If step 4 shows a denied loop, `errSecAuthFailed` is what the OS returns for an invalidated item: resolve it by checking the marker as `Invalidated` and update ADR-083 and the test `F-B-7`.
- Konsist (`InfrastructureDeviceRulesTest`): only domain/stdlib/platform imports, no database, SharedPreferences, DataStore or user-defaults API and no backed-up directory (`filesDir`, `cacheDir`, `getExternalFilesDir`, `dataDir`, `openFileOutput`, `getSharedPreferences`) in `securestore`; the Android record store touches files only in `RecordFiles`, below `noBackupFilesDir`; no `Secret` in `platform`; no printing or `android.util.Log`; fixed public surface. Planted-violation tests cover each form.

## Attention, decision, approval and budget gateways (Phase 1b-4a)

- **Shape.** `AttentionGatewayAdapter`, `DecisionGatewayAdapter`, `ApprovalGatewayAdapter`, `BudgetGatewayAdapter` in `shared/infrastructure/api`. Each takes the `PaperclipHttpClient`, the `InstanceRepository` and the `SecretStore`; `CompanyCalls` reads the factory's address, pins and key from the scope's instance for each call (the key is wiped after it), so a call can only reach the instance that owns the scope. The company id goes in the path for feed, dismissals, triage and budgets; decisions and approvals are addressed by id only and are checked against the scope's company (ADR-057).
- **DTOs** (`dto/`, all internal): every property optional or defaulted, `ignoreUnknownKeys`; polymorphic parts (details, effects, payloads, metadata) are `JsonObject` read by `JsonReading.kt` helpers (ADR-055). Mappers turn them into domain types or null, which the adapter reports as `Malformed`. Money is parsed from the number's literal and rounded up to whole cents (`ceilToCents`, ADR-054).
- **Reads send once; writes send once.** Retrying a read is the use case's job. A write that needs a precondition (resolve a budget incident, approve, decide, dismiss) does one preceding read of the same resource, then one POST (ADR-056, ADR-057). `decide` always carries its idempotency key.
- **Calls.** Feed `GET companies/{c}/attention?sort=decide&limit&cursor`; dismiss/snooze `POST companies/{c}/inbox-dismissals`; restore `DELETE companies/{c}/inbox-dismissals/{key}` (204); decide-by `PUT companies/{c}/decision-triage/{kind}/{id}` with `{"decideBy":null}` to clear; `GET decisions/{id}`, `POST decisions/{id}/decide|dismiss`; `GET approvals/{id}[/issues|/comments]`, `POST approvals/{id}/approve|reject|request-revision|comments`; `GET companies/{c}/budgets/overview`, `POST companies/{c}/budget-incidents/{id}/resolve`.
- **Tests.** `WorkWorld` (two factories, key roles owner of Acme and viewer of Globex) over `StubPaperclipServer`, which delegates company-scoped paths to per-domain stubs (`StubAttention`, `StubDecisions`, `StubApprovals`, `StubBudgets`) that hold state and follow the server rules read from source. The shared contract suites for the four ports run unchanged against the real adapters on JVM, Android host and iOS simulator. Fixtures (`FeedFixtures`, `DecisionFixtures`, `ApprovalFixtures`, `BudgetFixtures`) are written from server source and are not recorded; each states the server file and line it follows.

## Dashboard, agent, run, issue and interaction gateways (Phase 1b-4b)

- **Source of truth.** The pinned release's compiled dist (`@paperclipai/{server,shared,db}/dist`), not the newer dev tree 1b-4a used. ADR-060; the corrections are in `specs/261102-phase-1b-adapters/research.md`. The stub follows the server's quirks (cancel of an ended run answers 200, the log omits `nextOffset` on its last chunk, comments are newest first, create may be answered `deduplicated`), so the adapters' compensations are what make the shared suites pass.
- **Shape.** `DashboardGatewayAdapter`, `AgentGatewayAdapter`, `RunGatewayAdapter`, `IssueGatewayAdapter`, `InteractionGatewayAdapter` in `shared/infrastructure/api`, on the same `CompanyCalls`. `OwnedCalls.kt` (`requireIssue`, `provingOwnership`) and `ListReads.kt` (`allOrNone`, `ofCompany`) are the shared ownership helpers; `IssueRequests` and `InteractionRequests` build the request bodies key by key (explicit nulls matter to the server).
- **Ownership (ADR-061).** Agents, runs, issues, attachments and interaction answers have no company in the path. Non-uuid id: NotFound, no request. Single resource: the reply's `companyId` must be the scope's. Mutation: a read of the resource first, then one write. List of rows that name their company: checked per row; an empty one asks the issue. `issues/{id}/runs`: the issue is read first.
- **Calls.** Dashboard `GET companies/{c}/dashboard`, `.../costs/window-spend`. Agents `GET companies/{c}/agents` (no query), `GET agents/{id}`, `POST agents/{id}/pause|resume|heartbeat/invoke`, `PATCH agents/{id}/budgets`. Runs `GET heartbeat-runs/{id}`, `.../events?afterSeq&limit=500`, `.../log?offset&limitBytes=65536`, `POST .../cancel`, `GET issues/{id}/runs`, `GET companies/{c}/heartbeat-runs?agentId&limit=50`, `GET companies/{c}/live-runs`. Issues `GET companies/{c}/issues?view=compact&limit&offset[&status|attention|assigneeUserId=me|q|parentId]`, `GET issues/{id}`, `GET|POST issues/{id}/comments` (`order=asc`), `PATCH issues/{id}`, `POST companies/{c}/issues` (`allowDuplicate: true`), `GET issues/{id}/attachments`, and the adapter-only `GET attachments/{id}/content` with `Range`. Interactions `GET issues/{id}/interactions`, `POST .../interactions/{i}/accept|reject|respond|verdicts|skip`.
- **Runs.** The log offset is in bytes; the adapter computes the next offset on the last chunk (ADR-062). Cancel reads first and treats an ended run as a Conflict.
- **Attachments.** `IssueGatewayAdapter.attachmentContent` is public but not on a port (ADR-064); the client's `sendBytes` keeps the body as bytes. A slice is at most `AttachmentRanges.MAX_SLICE_BYTES` (1 MiB): an open-ended request is cut to one slice, a longer closed range is Rejected before any request, and a reply over the cap (a proxy that ignored `Range`) is Rejected while the body is read through a bounded channel, not buffered (F-A-7). A path segment of `.`, `..` or empty is NotFound before any request (F-A-9); a rejection's `reason` has credential-shaped text (`pcp_...`, bearer headers, urls, `token=` values, 24+ character key runs) replaced by `[removed]` (F-C-5); an approval with no linked issues or comments costs one extra ownership read (F-A-10); the real OkHttp engine is proven not to follow a 302 (`RealEngineRedirectTest`, F-A-8).
- **Interactions.** Five kinds are answerable; the rest are `UnsupportedInteraction` and never sent anything (ADR-065).
- **Tests.** Stubs per domain extend `StubPaperclipServer` through `StubWork`: `StubDashboard`, `StubAgents`, `StubRuns` + `StubRunHandlers`, `StubIssues` + `StubIssueList` + `StubThread`, `StubInteractions`; fixtures `DashboardFixtures`, `AgentRowFixtures`, `RunFixtures`, `IssueRowFixtures`, `InteractionFixtures`, each naming the dist file it follows. The existing shared suites (`DashboardContract`, `AgentContract`, `RunReadContract`, `RunWriteContract`, `IssueReadContract`, `IssueWriteContract`, `InteractionContract`) run unchanged through thin `*GatewayContractTest` subclasses on JVM, Android host and iOS simulator. `CompanyScopedAuditTest` calls every method of every company gateway for two factories and against a foreign company.



## The live contract test (`contractTest`, AD-050, AD-051)

`shared/infrastructure/api` has a JVM-only `contract` compilation (`src/contractTest`, associated with `main`) and a Gradle task `contractTest`. It is **not** part of `check` or `allTests` (it needs a server); `check` only compiles it. It runs the production adapters (`HealthGatewayAdapter`, `AuthGatewayAdapter`, the company gateways) on the real OkHttp engine with a test-only in-memory `SecretStore`, and `allowInsecureLocal = true` for `http://localhost:3199` (`127.0.0.1` is not on the allow-list; the test rewrites it).

Run it locally against the pinned container:

```bash
./scripts/paperclip-test-server.sh up
export PAPERCLIP_CONTRACT_BOOTSTRAP_INVITE="$(./scripts/paperclip-test-server.sh invite)"
PAPERCLIP_CONTRACT_I_KNOW_THIS_MUTATES=true PAPERCLIP_CONTRACT_BASE_URL=http://localhost:3199 ./gradlew :shared:infrastructure:api:contractTest
./scripts/paperclip-test-server.sh down
```

Without `PAPERCLIP_CONTRACT_BASE_URL` the live tests are skipped with a message (CI sets `PAPERCLIP_CONTRACT_REQUIRED=true`, which makes a missing server a failure). **The run mutates the server it talks to** (fixed test account, sign-up, invite, companies, agents, cost events, cancelled runs), so it refuses to start unless `PAPERCLIP_CONTRACT_I_KNOW_THIS_MUTATES=true` is set (contract.yml sets it; so does the line above), the url is plain http on `localhost`/`127.0.0.1` at the test server's port (3199, or `PAPERCLIP_TEST_PORT`), and `/api/health` reports authenticated and private. The throwaway compose has no server-side marker field the health reply could show, so the guard is these four conditions, checked before the first request (F-C-8, ADR-081), plus a positive identity (ADR-087): a fresh server must accept the invite minted inside the test container, a server in use must accept sign-in with the fixed test account (the run never signs up on it), and port 3100 is refused even with `PAPERCLIP_TEST_PORT`. What the run does: `ServerBootstrap` signs up the fixed test user and accepts the bootstrap invite (idempotent: an existing user signs in, an already bootstrapped server skips the invite); `Pairing` creates a challenge through the adapter, approves it with the session cookie and polls to approved; two companies, issues, approvals (one linked to an issue, one with a comment), agents (a `true`, an `echo` and a `sleep` process, and a spender), an attachment, a pending question, a cost event and an over-budget incident are seeded with the paired key or by the server itself; the tests read through every gateway, mutate each seeded object once, compare the error shapes and check that the second company is refused under the first company's scope. At the end the run prints, and writes to `shared/infrastructure/api/build/reports/contract/live-operations.txt`, the count verified **with data** (a non-empty decoded reply), the operations that were only reachable but empty, FAIL, SKIPPED and `MISMATCH n` (printed even when 0), and a `VERDICT:` line. The `contractTest` task fails on `VERDICT: FAIL`: any failed call, any mismatch, any operation that never ran or only decoded an empty reply, unless it is on the allow lists in `LiveOperations.kt` with a written reason (today only the three `DecisionGateway` operations: decisions are created inside an agent run, `POST /decisions` answers 403 to a board key). The `pinned` and the nightly `latest` job both run this task, so API drift turns the scheduled run red (ADR-082). The run found that a resume is answered mid-transition (ADR-074). Dispatching `contract.yml` by hand (`gh workflow run contract.yml --ref <branch>`) also runs the `latest` job. ADR-071 to ADR-074 explain the choices.
